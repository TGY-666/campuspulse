## 0. 版本变更：这一版改了什么，为什么

### 0.1 四次调整：v1.0 → v1.2

| 项 | v1.0 | v1.2 | 理由（决策记录） |
|---|---|---|---|
| 多租户 | 完整多租户（5 角色 + 平台运维 + SaaS 化） | **降级为轻量多租户**（4 角色、无管理后台、CLI 开户） | 单校私有化是当前真实形态；SaaS 那层（注册、计费、平台运维）在比赛周期内无法验证，属于"做了也没人用" |
| 实时爬虫 | 整章（M2） | **删除** | ①与"AI Web 网页开发"赛道无对应得分项；②采集第三方平台存在 ToS 与合规风险，作为比赛作品提交不合适 |
| 原生 App | 整章（M5，推荐混合方案） | **删除** | 评分细则 6 维度 18 个考察点中无"原生/多端"一项，估算贡献 ≤2 分；且赛道为 Web，存在"跑题"风险 |
| 多 Agent 协作 | 完整 5 角色 DAG（7 人日） | **降级为"Agent 可靠性增强"**：只保留引用硬阻断（1 人日） | 5 个角色里 4 个是把现有的一次 ReAct 循环拆成 4 段对话；唯一单 Agent 做不到的是**独立复核**。为此付 3–4 倍调用成本不划算，见 **4.1** 与附录 D.3 |

保留的决策依据见 **附录 D**（含实测数据、逐条评分对照、答辩话术），不是"拍脑袋砍掉"，被老师或评委问起可直接翻。

## 1. 总体设计

### 1.1 三项能力的位置

```
┌────────────────────────────────────────────────────────────┐
│  M1 轻量多租户（横切）：谁登录、什么角色、能看到哪些数据      │
└────────────────────────────────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
  数据/统计层        M4 Agent 可靠性增强    M3 处置工单
  （v1.0 不动）      生成→核验→重答→标注    建单→派单→处理→归档
                            │                   ▲
                            └── 结论/证据 ───────┘
```

三项之间是**弱耦合**：M1 是前置（没有角色就没有工单的派单对象），M3 与 M4 互不依赖，可并行开发。

### 1.2 落地顺序

| 顺序 | 能力 | 理由 |
|---|---|---|
| ① | **M1 轻量多租户** | 横切维度。后做等于给所有表、接口、缓存键返工一次 |
| ② | **M3 处置工单** ∥ **M4 Agent 可靠性增强** | 二者无依赖；M4 现在只有 1 人日，**推荐插在 M3 的中途做**（换脑子的活），不单独占一个阶段 |

| 编号 | 约束 | 怎么检查 |

| **C3** | 离线可跑 | 断网能启动、5 个页面能开、演示链路完整（AI 降级为规则模式） |

### 1.6 数据库演进策略

**不做分库，做"单库 + tenant_id + 强制注入"。** 数据量（2.5 万行）远未到分库门槛，
而分库会毁掉"删库自愈""单文件可拷走"两个私有化卖点。

轻量版不引入完整的 `schema_version` 表，改用**幂等升级函数**（够用且更少出错）：

```python
def upgrade():
    """可重复执行；已存在则跳过。启动时必跑一次。"""
    _ensure_column("datasets", "tenant_id", "TEXT DEFAULT 't_default'")
    _ensure_column("comments", "tenant_id", "TEXT DEFAULT 't_default'")
    # ... 其余表同
    _ensure_index("idx_comments_tenant", "comments", ("tenant_id","dataset_id","cleaning_status"))
    # 无列则加列，有列则跳过；索引同理
```

> `_ensure_column` 内部用 `PRAGMA table_info(<table>)` 判断，**不依赖记忆版号**。
> 2.5 万行规模下整套升级应 **< 3 秒**，超过 10 秒要查索引重建方式。

**老库升级的 4 步**（SQLite 不能 `ALTER` 主键，需要时按 6 步重建，见附录 A 注）：

1. 5 张业务表补 `tenant_id DEFAULT 't_default'`；
2. `UPDATE ... SET tenant_id='t_default' WHERE tenant_id IS NULL;`
3. 重建索引，全部改为 `(tenant_id, ...)` 前缀；
4. 插入默认租户行 + 建首个管理员账号（见 FR-M1-07）。

**S1 期间发现并修掉的 4 个真问题**（都会在 S2 复用同样的模式）：

1. **启动期没有租户上下文 → 数据归属被写成空串**。`create_app()` 里的 `init_db` / `bootstrap_presets`
   不属于任何请求，`current()` 返回"未登录"身份（`tenant_id=""`），导入的数据全进了空租户，
   所有租户都查不到。修法：启动期显式 `tenancy.set_context(system_context())`。
   **不能靠 `db.tid()` 自动兜底成默认租户**——那样未登录请求也就顺带能读默认租户的数据了。
2. **`upsert_dataset` 的 `ON CONFLICT DO UPDATE` 会覆盖 `tenant_id`**。归属不是可覆盖字段：
   允许它被覆盖，一次上下文错乱就能把整批数据集改到别的租户名下，且没有痕迹。
3. **`_where()` 的租户条件不能来自筛选项**。`f` 是用户可控的（前端/Agent 传参），
   租户只能来自会话上下文。把租户塞进筛选参数表，等于把越权入口做进了参数表。
4. **强制闸门默认值改为跟随 `CP_AUTH`**。S0 时两者分开是必要的（那时 SQL 还没改）；
   S1 之后"开了登录却没开强制"是纯风险零收益状态，默认必须绑在一起。

> 第 4 条的连带效果：`CP_TENANT_ENFORCE=1` 把**验证脚本自己**的两条漏写 SQL 也揪了出来。
> 这不是麻烦，而是这条规则唯一可信的来源——**规则对写规则的人同样生效**。

**S2 期间发现并修掉的 4 个真问题**

1. **规则 R3 用"7 天总量"比"日均值"**。7 天总量约等于日均的 7 倍，
   `> 3 倍` 恒成立——这条规则会天天报警，且从结果上看"总能发现问题"。
   改成同长比较（近 7 天总量 vs 前 7 天总量），并给稀疏数据补 `skipped` 理由。
2. **`visible_pages()` 被引用但没定义**。404 页渲染直接 500，`acceptance.py`
   的「404 处理」项当场变红。教训：`render_template` 里的名字找不到只会 500，
   不会在启动时暴露——页面类回归必须真去 GET 一次。
3. **权限表与状态机打架**。`PERMS["admin"]` 没有 `ticket_handle`，
   但状态机允许 admin「开始处理 / 提交复核」。当时没有功能影响（`can_handle()`
   只用于两个已被 `can_view_any()` 覆盖的地方），但只要有人加一句
   `if not can_handle(): raise`，就会变成"管理员点不动自己的按钮"。
   两处规则不一致，早晚要有一次以 bug 的形式结算。
4. **空租户建单报错原因说错**。租户校验排在"取证据"之后，空上下文先撞上
   "数据集不存在"（按 `tenant_id=''` 查不到数据集）。把租户校验提到最前面：
   报错原因必须和真实原因一致，否则排查会往数据迁移方向白跑。

**一个刻意的取舍**：工单建议**不自动建单**。自动建单等于机器替人定性
（"某校食堂出了问题"应由人看完证据后说）。系统只摆事实：命中哪条规则、
依据哪几个数字、代表证据是哪几条；建不建、定几级由人点。

**S3 期间发现并修掉的 3 个真问题**

1. **改写稿作为底稿继续剔除时，用的是第一版的问题清单。**
   第一版里越界的编号，经过一次改写后可能已经换对了；沿用旧清单会把它
   从"已经改对"的回答里再删一遍。修法：替换底稿时同步换成改写稿自己的问题清单。
2. **AI 回答未通过数字校验、被替换成规则陈述后，`grounding` 没有重算。**
   结果是"正文是规则陈述、角标却写着需复核"，两者描述的不是同一段文字。
   验收里有一条断言正好卡在这里（`payload["grounding"]["passed"]`），
   平时不触发，一旦触发就是自相矛盾的展示。
3. **前端 `run.verdict is not a function`。** 事件分发加了分支，方法却没进 `run` 对象——
   `consumeStream` 抛错 → 整轮回答一个字都不渲染，但控制台里只有一行
   "实时通道不可用"。教训：前端新增事件类型，**必须真点一次**，
   `node --check` 只查语法，查不出"方法不存在"。

**两处与规格的偏差（有意为之）**

| 项 | 规格 | 实现 | 原因 |
|---|---|---|---|
| `verdict` 取值 | 4 个 | **6 个**（多 `flagged`、`unverified`） | 只记录模式和核验器故障时，用 `pass` 会撒谎。宁可多两个状态，也不用"通过"覆盖"没验过" |
| 答辩演示动作 | 等模型编造编号 → 角标变 ⚠ | 改成"正常问答看 `pass` 明细"+"跑 verify_agent 看拦截" | 实测模型会老实回答"匹配 0 条"，角标是 `no_anchor` 不是 ⚠。**不赌模型行为的演示才可靠** |

**一处配置调整**：`CP_CITATION_GUARD` 默认值从 0 改为 **1**。
原计划"P2 开关全部默认关 = 行为与 v1.0 一致"，但这个开关只做减法
（不改统计、不改图表，最坏是少一句话）；默认关意味着"能拦住编造引用"
在默认配置下不成立。关闭态由 AC-M4-08 单独覆盖，可一键回退。

## 2. M1 轻量多租户（可登录 · 分角色 · 数据隔离）

### 2.1 "轻量"到底轻在哪（先把边界钉死）

| 维度 | 完整多租户（v1.0 方案） | **轻量多租户（本期）** |
|---|---|---|
| 租户共存 | ✅ 多校共用一套部署 | ✅ 支持，但靠命令行开户，无管理后台 |
| 数据隔离 | 强制 + 可验证 | **强制 + 可验证（一点不省）** |
| 角色 | 5 个（含平台运维、租户管理员） | **4 个**（admin / analyst / handler / viewer） |
| 自助注册 / 邀请 | 有 | ❌ 无 |
| 租户管理页面 | 有 | ❌ 无（CLI 一条命令） |
| 计费 / 配额 | 有字段 | ❌ 无 |
| API Token | 有（给 App 与脚本） | ❌ 无（App 已砍；脚本直接用 Cookie 或临时 Token 另议） |
| 跨租户切换 UI | 有 | ❌ 无 |
| 单点登录 | 规划中 | ❌ 无 |

**一句话**：轻量 = **把"隔离"做扎实，把"运营"全砍掉。**
隔离是正确性问题（不可省），运营是产品化问题（可延后）。

> 答辩被问"你说多租户，但只能命令行开户，这算多租户吗？"——
> 标准答案是："多租户的实质是**数据隔离可证明**，开户方式是运营层的便利性。
> 我们优先保证前者：有一个脚本在用 32 次交叉访问证明 A 校看不到 B 校。"

### 2.4 数据模型

```sql
CREATE TABLE tenants (
    tenant_id   TEXT PRIMARY KEY,              -- t_default / t_neusoft
    name        TEXT NOT NULL,
    short_name  TEXT,
    status      TEXT NOT NULL DEFAULT 'active',
    note        TEXT,
    created_at  TEXT NOT NULL
);

CREATE TABLE users (
    user_id      TEXT PRIMARY KEY,
    tenant_id    TEXT NOT NULL,
    username     TEXT NOT NULL,
    display_name TEXT,
    role         TEXT NOT NULL,                -- admin/analyst/handler/viewer
    pwd_hash     TEXT NOT NULL,
    must_change  INTEGER NOT NULL DEFAULT 0,

CREATE TABLE auth_events (
    event_id   TEXT PRIMARY KEY,
    tenant_id  TEXT,
    user_id    TEXT,

    created_at TEXT NOT NULL

CREATE INDEX idx_users_tenant ON users (tenant_id, username);
```

### 2.7 技术方案要点

**（a）隔离的强制手段**

`db.py` 现有 4 个入口（`query_all/query_one/scalar/get_conn`）全部要收口：

```python
PROTECTED = {"datasets","comments","reports","agent_runs","guard_events",
             "tickets","ticket_events"}

class TenantConn:
    def execute(self, sql, params=()):
        if _touches(PROTECTED, sql) and "tenant_id" not in sql.lower():
            if config.CP_DEV:
                raise TenantLeakError(f"SQL 未带 tenant_id：{sql[:120]}")
            logger.error("tenant_leak_suspected: %s", sql[:200])
        return self._raw.execute(sql, params)
```

三点要能讲：

1. **默认拒绝**：宁可开发时抛异常，也不要上线后悄悄查全库；
2. **生产只记录**：一个漏写不该把整站打挂（可用性取舍，要写进文档）；
3. **白名单**：只有 `tenants` 表与平台级统计允许不带 `tenant_id`。

**（b）缓存是最容易漏的地方**

三处缓存——RAG 索引（`rag.py`）、统计结果、词云缓存——键统一改为
`(tenant_id, dataset_id, filters_hash)`，且**只允许通过一个 `cache_key()` 函数生成**。
这条单独列 AC-M1-11。

**（c）会话实现（零依赖）**

Flask 自带 `itsdangerous.URLSafeTimedSerializer` 签名 `{uid,tid,role,iat}`，`max_age=8h`。
不需要服务端 session 表，也就不必引入 flask-login。

**（d）文件与报告**

`data/uploads/<tenant_id>/<yyyyMM>/`；报告 ID 改 `rpt_<tenant前6位>_<8hex>`，附件名保持人读标题。

## 3. M3 处置工单（从"看到了"到"有人管"）

### 3.1 定位与边界

把发现的问题变成**有负责人、有时限、有留痕**的内部流程。

**做**：建单、分派、处理记录、复核、归档、SLA 计时、复盘指标。
**不做**（写进页面免责区）：

- ❌ 不自动对外发布任何回应（只做内部流转）
- ❌ 不判定事件真伪、不对具体个人采取任何动作
- ❌ 不把工单结论等同于事实结论

> 标题栏下方固定一行灰字：
> `本工单为校内处置记录，不代表对相关言论真实性的认定；系统不对学生个人做任何标记或评分。`

### 3.2 关键前提调整（因取消实时爬虫）

v1.0 方案里"新数据进来 → 命中规则 → 自动建单"这条链依赖爬虫。**爬虫已取消，改为两种触发**：

| 触发方式 | 说明 | 优先级 |
|---|---|---|
| **人工建单（主路径）** | 在预警卡片 / 证据详情 / 洞察页任何一处点"建单"，带上当前口径与证据 | P0 |
| **规则建议建单（辅路径）** | 打开驾驶舱或证据页时，后端评估 4 条规则，命中则顶部提示"检测到 2 条预警，可一键建单"，**不自动建** | P0 |
| 定时批量评估（可选） | 每日 08:00 评估一次，生成待确认列表 | P2 |

> 这个改动其实更符合定位：**系统给建议，人做决定。**
> 自动建单会把"机器定性"的嫌疑引到作品上，人工一键建单反而更稳。

### 3.3 用户故事

1. 作为分析员，我在证据页看到"食堂餐饮本周负面 48 条、占比 25.9%"，点"据此建单"，
   选题主、优先级、写摘要，系统自动带上前提筛选口径 + 5 条代表证据。
2. 作为管理员，我在工单列表看到 3 个待分派，把 P0 派给后勤处置员，要求 4 小时内首次响应。
3. 作为处置员，我打开工单看到证据原文与口径，处理完写"已联系食堂承包商，本周加开窗口"，提交复核。
4. 作为管理员，我复核通过归档；系统记录"建单到归档 26 小时，SLA 内"。
5. 作为校领导，我在驾驶舱看到"待处置 3 / 超期 1"，点进去就是工单列表。

### 3.4 状态机

迁移规则表（**逐行实现，验收按此表跑全路径**）：

| from | to | 允许角色 | 必填字段 | 副作用 |
|---|---|---|---|---|
| draft | triaged | analyst, admin | 优先级、维度 | 起算 SLA |
| draft | rejected | analyst, admin | 驳回原因 | 记误报 |
| triaged | assigned | admin | owner_id（必须是 handler/admin） | 记通知 |
| triaged | rejected | admin | 驳回原因 | — |

| assigned | triaged | admin | 退回原因 | 清空 owner |

### 3.5 SLA

| 优先级 | 首次响应 | 归档时限 | 触发场景 |
|---|---|---|---|
| P0 紧急 | 1 小时 | 4 小时 | 负面率 > 2× 基线、安全类关键词 |
| P1 高 | 4 小时 | 24 小时 | 单维度负面 ≥ 20 且占比 ≥ 25% |
| P2 中 | 1 个工作日 | 72 小时 | 常规集中吐槽 |
| P3 低 | 3 个工作日 | 7 天 | 零散单条、正向建议 |

**计时算法（写清，否则"超时"口径会被当场追问）**：

- 只计**工作时间**：周一至周五 09:00–12:00、14:00–18:00；
- 节假日通过 `tenant.note` 同级配置项 `holidays` 提供（默认空，不猜）；
- 起算点：进入 `triaged` 的时刻；
- `pending_review` **继续计时**（复核拖延也是拖延）；
- `sla_due` 起算时一次性算出落库，展示"剩余 2 小时 10 分 / 已超期 3 小时"，不实时重算。

### 3.6 规则建议建单（与现有 `/api/analytics/risk` 对齐）

| 规则 | 条件 | 默认优先级 |
|---|---|---|
| R1 负面率突增 | 24h 负面率 > 近 30 天基线 × 2 | P0 |
| R2 单维度聚集 | 单维度负面 ≥ 20 且占比 ≥ 25% | P1 |
| R3 关键词突增 | 某关键词 24h 提及量 > 前 7 日均值 × 3 | P1 |
| R4 高互动负面 | 单条负面点赞 ≥ 500 | P2 |

**建议不落库**：命中后只在接口响应里返回 `suggestions[]`，用户点"建单"才写 `tickets`。
去重规则：同 `(dimension, rule_id)` 24 小时内已建过且未关闭 → 提示"已有同类工单 TK-xxxx"。

## 4. M4 Agent 可靠性增强（原"多 Agent 协作"降级）

### 4.1 决策：为什么不做完整的多 Agent

**先看现状。** v1.0 的 Agent 不是"一问一答"，已经是一个完整的多步循环（`agent.py:803`）：

| 已有能力 | 实现位置 | 说明 |
|---|---|---|
| 6 个工具 | `tools.TOOL_SPECS` | 情感统计、议题分布、时间趋势、平台对比、评论检索、RAG 混合检索 |
| 多步规划 | `for _ in range(AGENT_MAX_TOOL_CALLS + 1)` | 最多 6 次工具调用，90 秒总上限 |
| 同名同参去重 | `_seen_calls` | 重复调用复用结果，不重复执行 |
| 过程可见 | `stage / plan / tool_start / tool_done` | 前端实时显示"在想什么、要调哪个工具、跑了几毫秒" |
| 三级降级 | AI → 规则模式 | 断网/超时/无 Key 仍能出结论，数字仍来自数据库 |
| 引用校验 | `rag.citation_check` | 区分 valid / invalid / unknown，**但只记录不阻断** |

**再看多 Agent 要加什么。** 5 个角色拆开看：

| 角色 | 实质工作 | 单 Agent 等价物 | 是否真增量 |
|---|---|---|---|
| orchestrator | 拆解问题、决定查什么 | 已有，就是 `plan` 事件 | ❌ 换个名字 |
| data | 调统计工具取数 | 已有 | ❌ 换个名字 |
| evidence | 调 RAG 取证 | 已有 | ❌ 换个名字 |
| advisor | 按证据写结论 | 已有 | ❌ 换个名字 |
| **critic** | **独立复核引用与数字能否溯源** | **没有** | ✅ **唯一真增量** |

**结论：不做完整多 Agent，只做 critic 那一块。**

代价不是"多一点工作量"，而是三样具体的东西：

| 代价 | 具体 |
|---|---|
| 成本 | 3–4 次 LLM 调用，token 约 2.5 倍 |
| 延迟 | DAG 串行段累加，复杂问题反而比单 Agent 慢 |
| 新增失败模式 | Agent 之间传话会丢信息——这是多 Agent 系统最典型的幻觉来源，只能靠"只传结构化 claim"缓解，无法消除 |

为"我们有 5 个 Agent"这个说法付这些代价，不划算。

> **一条可复用的判断标准**：拆分只有在子任务需要**不同权限**或**不同模型**时才有收益。
> 这里 5 个角色用同一个模型、同样的数据权限，拆开只是多绕几圈——**这叫分段，不叫协作。**

### 4.2 本期范围：只做三件事

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-M4-01 | **引用硬阻断**：回答中的编号若不在本次检索结果内，先重答一次；仍不通过则剔除并标注 | P0 |
| FR-M4-02 | **数字核验统一**：把散在 `agent.py` 的数字比对逻辑收拢到 `veracity.py` 单一入口 | P1 |
| FR-M4-03 | **核验结果可见**：前端在回答下方显示"引用核验"角标，可展开看明细 | P0 |

**非目标**（明确不做，避免执行时又扩）：

- ❌ 多角色 DAG、Agent 间消息总线、并行取证
- ❌ 协作时间线泳道图
- ❌ token 预算分配与成本看板
- ❌ `agent_runs` 新增 trace 字段

### 4.3 判定规则

沿用现有 `citation_check` 的三分类，但**处置方式从"记录"改为"干预"**：

| 状态 | 含义 | 处置 |
|---|---|---|
| `valid` | 编号在本次检索结果中 | 保留，前端可点击回跳原文 |
| `invalid` | 编号在库里存在，但**未被本次检索命中**（越界引用） | 剔除该编号 → 触发重答 |
| `unknown` | 编号在库里**根本不存在**（编造） | 剔除该编号 → 触发重答 |
| 无任何编号 | 回答未标注引用 | 不重答，标注"结论未标注原文锚点" |

**数字核验**（已有逻辑，保持硬拦截）：回答里出现的统计数字，必须能在本轮工具结果中找到同值；找不到 → 该数字所在句子降级为定性表述（"较多""部分"），不写具体数值。

**一句话原则**：**宁可说得少，不可说得假。** 降级后的回答信息量下降，但每一句都能在系统里点开验证。

### 4.4 重答与降级链

```
生成回答
   │
   ├─ citation_check → 全部 valid ────────────────────▶ 正常输出（角标：引用 5/5 已核验）
   │
   └─ 存在 invalid / unknown
          │
          ├─ 第 1 次：带"只许引用以下编号"的约束重答（≤1 次，不循环）
          │      │
          │      └─ 复核通过 ────────────────────────▶ 正常输出（角标：已修正 2 处引用）
          │
          └─ 仍不通过
                 │
                 ├─ 剔除问题编号，输出剩余内容 ──────▶ 角标：⚠ 2 处引用无法溯源，已移除
                 │
                 └─ 若全部编号都有问题，或回答本就没有编号
                        │
                        └─ 降级为"仅统计陈述" ────────▶ 角标：⚠ 结论缺少原文锚点
```

**三条硬约束**：

1. **重答最多 1 次**。不循环、不递归——否则一个坏问题能烧掉整轮预算。
2. **重答不重新检索**，复用本轮已取到的片段，避免"越查越乱"。
3. **任何降级都要显示**。前端角标必须出现，不允许静默丢弃内容（与 v1.0"降级要说"一致）。

### 4.5 接口与事件

不新增接口，只在现有响应体与 SSE 事件里加字段。

**`POST /api/agent/chat` 响应新增**：

```json
{
  "answer": "...",
  "citation": {
    "total": 5, "valid": 5, "invalid": [], "unknown": [],
    "verdict": "pass",
    "revised": false,
    "removed": []
  }
}
```

`verdict` 四个取值对应四种角标，**前端不需要自己推断状态**：

| verdict | 含义 |
|---|---|
| `pass` | 引用全部命中，无需干预 |
| `revised` | 触发重答且复核通过 |
| `stripped` | 重答后仍不通过，已剔除问题编号 |
| `no_anchor` | 无引用标注（内容照常输出，只做提示） |

**SSE 新增一个事件**（其余不变）：

| 事件 | 负载 | 前端表现 |
|---|---|---|
| `verdict` | `{verdict, total, valid, removed[]}` | 回答下方角标；`revised` 时多一行"已自动修正 N 处引用" |

> 不在 token 流中间插入事件，避免打断打字机效果——`verdict` 一律在 `done` 之前发一次。

### 4.6 前端表现

四种角标，样式沿用现有 `.cp-badge` 体系：

| verdict | 角标文案 | 颜色 | 展开内容 |
|---|---|---|---|
| `pass` | ✓ 引用 5/5 已核验 | 成功色 | 每条编号 → 对应原文 |
| `revised` | ✓ 已自动修正 2 处引用 | 成功色 | 修正前 / 修正后 |
| `stripped` | ⚠ 2 处引用无法溯源，已移除 | 警告色 | 被移除的编号及原因 |
| `no_anchor` | ⚠ 结论未标注原文锚点 | 警告色 | 提示"可追问这条结论的依据" |

**答辩演示动作**（约 30 秒，比讲架构有力得多）：

> 从别的数据集挑一个编号，问 AI"这个编号的评论说了什么"→
> 若它编造引用 → 角标立刻变 `⚠` → 展开给评委看"这个编号系统里不存在，被拦下来了"。

> **S3 实测后的修正（重要）**：这个动作不可靠。当前模型会老实回答
> "按编号 CMT-xxx 检索，匹配评论为 0 条"，角标是 `no_anchor` 而不是 `⚠`。
> 演示改成不赌模型行为的两步：① 正常提问看 `✓ 引用 3/3 已核验` 并展开明细；
> ② 当场跑 `tools/verify_agent.py`，看 AC-M4-02 把编造编号从回答里剔掉。
> 前者证明"可信"，后者证明"可拦"，都不依赖模型这一次是否恰好犯错。

### 4.7 验收标准

| 编号 | 断言 |
|---|---|
| AC-M4-01 | 正常问答：`citation.valid == total`，`verdict == "pass"`，回答内容不受影响 |
| AC-M4-02 | 注入编造编号（`[CMT-NOTEXIST]`）→ 该编号不出现在最终回答中，`verdict == "stripped"` |
| AC-M4-03 | 注入越界编号（库里存在但未被检索到）→ 归入 `invalid` 而非 `unknown`，两者不混 |
| AC-M4-04 | 触发重答时 LLM 调用次数 = 2（不是 3），且第二次不重新检索 |
| AC-M4-05 | 重答成功 → `revised == true` 且 `verdict == "revised"`，角标显示修正条数 |
| AC-M4-06 | 整段无编号 → `verdict == "no_anchor"`，正文**照常输出**（不因缺锚点删内容） |
| AC-M4-07 | 回答中的统计数字全部能在本轮工具结果中找到（0 处未匹配） |
| AC-M4-08 | `CP_CITATION_GUARD=0` → 响应体与 v1.0 逐字段一致（仅多 `citation` 字段，为只记录模式） |
| AC-M4-09 | 引用校验环节抛异常 → **放行原文**并记日志，绝不让整轮对话失败 |
| AC-M4-10 | 并发 4 轮问答，`citation` 各自独立、不串 |

> AC-M4-09 是这条链路上最容易写错的地方：**校验器比被校验的内容更容易挂**。
> 校验失败时应退回"不校验"，而不是"拒绝输出"。

### 4.8 不做多 Agent，答辩怎么讲

被问到"为什么不做多 Agent"时，**不要辩解，直接给判断**：

> "我们评估过。拆成 5 个角色，其中 4 个是把现在一次完成的事拆成四段对话；
> 唯一单 Agent 做不到的是独立复核——所以我们只做了复核这一块。
> 代价是 3 倍调用成本和新的失败模式，收益是系统能拦住 AI 编造的引用。
> **我们把力气放在后者，因为它能被当场验证。**"

三个要点建议背下来：**承认评估过 / 说清唯一增量 / 给出可验证证据**。
它比"我们实现了多 Agent 协作"更难得——评委见过太多声称用了多 Agent 的队伍，
很少见到能说清"为什么可以不用"的。

**工作量：1 人日**（`veracity.py` 与重答逻辑 0.5、前端角标 0.3、验证 0.2）

| 3 | 工期超支产出"半成品功能" | 中 | 高（比不做更糟） | 每项独立开关 + 门禁 | 砍工单的 P2 项，保 M1+M3 主链 |

> 第 2 行值得单独说：**"AI 编造"是它能修的问题，"校验器误杀"是它引入的问题。**

> 所以整个 M4 的设计原则是"**校验失败时退回不校验，绝不拒绝输出**"——
> 宁可漏掉一次编造，也不能让正常回答消失。

**不要砍的**：32 次隔离矩阵。它看起来最像"额外工作"，但它是唯一能证明"越不了权"的东西——
砍了它，多租户就从"能力"退回成"声明"。

## 附录 D｜决策记录：为什么不做实时爬虫、不做原生 App、不做多 Agent

> 留档。被老师问"为什么别人都有爬虫你没有""为什么不做多 Agent"时可直接翻。

### D.1 实时爬虫

**实测结论（2026-10-30 本机）**：

| 环节 | 实测 |
|---|---|
| 采集器 import / 浏览器启动 | 1.85s / 1.4s（热）· 7.1s（冷） |
| 清洗 5,000 条 | 0.488s（0.10ms/条） |
| 入库 2,000 行 | 0.018s（0.01ms/行） |
| **清洗 + 入库 200 条** | **≈22ms** |
| 真爬一轮（15 条笔记 + 抓评论 + 每条 sleep 2s） | **60–90s**，登录失效再 +1–2 分钟，风控则 0 产出 |

**砍掉的三条理由**：

1. **得分**：评分细则 18 个考察点里没有"数据采集"，能沾的只有"场景真实性 5%"，
   而这 5% 靠"真实 25,699 条历史数据 + 可复算口径"已经拿到了；
2. **合规**：采集第三方平台数据涉及平台 ToS，作品若被传播存在风险；作为比赛作品不合适；
3. **演示**：60–90s 换 20–50 条有效数据，观感收益极低，且失败即事故。

**替代叙事（答辩直接说）**：

> "数据来源是项目内已有的真实采集文件，我们不把'能爬'当卖点。
> 系统设计上采集是适配器，接学校自己的后勤报修、教务评教、企业微信反馈群更合规、更稳定——
> 这也是我们在商业价值里写的'长期应由授权渠道供数'。"

> 附带留档：本机 MediaCrawler 曾在 Git Bash 下起不来，根因是 `PATHEXT` 为空导致
> execjs 找不到 `node.exe`（`Could not find an available JavaScript runtime`）。
> 若将来要做采集，先补这个环境变量。

### D.2 原生 App

| 评分维度 | 权重 | 原生 App 贡献 |
|---|---|---|
| AI 技术深度 | 35% | **0**（分项与端无关） |
| 创新性 | 25% | 0–0.5（"有 App"不算模式创新） |
| 前端工程质量 | 10% | **0**（分项是 TS / 组件化 / 首屏性能，均为 Web 指标） |
| 实用性 | 10% | 0.5 |
| 用户体验 | 10% | ≤1（"响应式适配"里的一小块，390px 已做完并验证） |
| 社会价值与商业 | 10% | 0.5 |
| **合计** | 100% | **≈1–2 分（上限）** |

另有两个风险：①赛道为 **AI Web 网页开发**，交 App 会被问"这是 App 还是 Web"，答不好是减分；
②双维护成本，答辩后基本不再更新。

**保留的替代方案（不写代码也算能力）**：答辩 PPT 写"演进路线：Web → PWA → 原生 App（采购后）"。
如果还有 1 天，做 PWA（`manifest.json` + `sw.js`）比做 App 划算：可装主屏、可离线、仍是 Web 技术。

### D.3 多 Agent 协作

**结论：不做 5 角色编排，只做 critic（独立复核）。7 人日 → 1 人日。**

**依据一：5 个角色里 4 个是换名字。**

v1.0 的 `agent.py:803` 已经是一个完整的多步循环：6 个工具、最多 6 次调用、90 秒上限、
同名同参去重、`plan → tool_start → tool_done` 全程可见、AI 失败降级规则模式。

| 角色 | 单 Agent 里对应什么 | 是否新增能力 |
|---|---|---|
| orchestrator | `plan` 事件 | 否 |
| data | 4 个统计工具 | 否 |
| evidence | `search_comments` + `retrieve_context` | 否 |
| advisor | 最后一轮生成 | 否 |
| critic | **没有对应物** | **是** |

把一件事拆成四段对话来完成，**叫分段，不叫协作**。

**依据二：代价是具体的，收益是概念的。**

| 项 | 多 Agent | 单 Agent |
|---|---|---|
| LLM 调用 | 3–4 次 | 1–2 次（复杂问题） |
| token | 约 2.5 倍 | 1x |
| 延迟 | DAG 串行段累加 | 单轮，最短 |
| 新增失败模式 | Agent 传话丢信息（幻觉来源） | 无 |

**依据三：评分表看的是"Agent 自主规划与工具调用"，不是"Agent 数量"。**
细则里没有"多 Agent"这个词。而且"我们用了 5 个 Agent"是一句**无法验证**的话；
"它编的引用会被系统拦下来，你现在可以试"是**能当场验证**的。
后者在"技术方案创新 8%"和"解决方案有效性 5%"上更站得住。

**依据四：拆分的收益条件不满足。**
拆分子任务只有在需要**不同权限**（如一个能查库、一个不能）或**不同模型**（如一个用大模型规划、小模型执行）时才有意义。
这里是同一个模型、同一套数据权限——拆开只剩开销。

**答辩话术（建议背下来）**：

> "我们评估过，也写了完整方案。拆成 5 个角色，其中 4 个是把现在一次完成的事拆成四段对话；
> 唯一单 Agent 做不到的是独立复核，所以我们只做了复核这一块。
> 代价是 3 倍调用成本和新的失败模式，收益是系统能拦住 AI 编造的引用。
> **我们把力气放在后者，因为它能被当场验证。**"

v1.0 的完整设计（角色定义、claim 契约、预算、熔断）在本文档 v1.0/v1.1 版本里可查，不必从零设计。
