## 二、为什么这样组织提交

### 不是"按文件类型"，而是"按模块边界"
`feat(db)` → `feat(etl)` → `feat(analytics)` → `feat(rag)` → `feat(agent)` → `feat(safety)`
这条链就是数据的真实流向：**入库 → 清洗 → 统计 → 检索 → 编排 → 核验**。
按这个顺序读提交历史，能看出系统是怎么一层层搭起来的，而不是"先写了个 all.py 然后拆开"。

### 每个提交信息都写"为什么"，不只写"做了什么"
例：`feat(safety)` 的说明里写了"为什么比规格多两态"——因为「模型没编、但也没引用」
和「引用指向不存在的评论」是两个不同的问题，合并会丢诊断信息。
评审想看的正是这类判断，而不是 `update code`。

### 三个提交承担"讲故事"的作用
- **03 `feat(v0)`**：保留单页大屏原型，用于对照迭代路径（后来补了 23 项验收才敢扔掉的功能，原型里都没有）
- **11 `feat(safety)`**：这是全项目最有辨识度的技术点，单独成一次提交，便于评审定位
- **20/21 `test`**：测试与验收独立成批次，表明"数字是被验证过的"，不是事后补的

## 三、如何核查（给评审）

```bash
# 1. 看整体脉络
git log --oneline --no-decorate

# 2. 看某次提交改了什么
git show 42bdd6b --stat

# 3. 确认没有密钥泄露（应无输出）
git log --all -p | grep -iE "sk-[a-zA-Z0-9]{20,}"

# 4. 确认敏感文件未被跟踪（应无输出）
git ls-files | grep -E "^\.env$|\.db$|demo_accounts|session_key"

# 5. 从零复现（需 Python 3.10+）
cp .env.example .env      # 填入 DEEPSEEK_API_KEY
# Windows 直接双击 start.bat；或：
.venv/Scripts/python.exe run.py
```

> 数据集在仓库内（`comparison_data/`，约 12 MB），首次启动会自动清洗入库，
> 无需外部下载即可复现全部图表与 AI 问答。

## 四、后续提交规范

| 前缀 | 用于 |
|---|---|
| `feat(模块)` | 新功能 |
| `fix(模块)` | 修 bug，说明里必须写"怎么复现的" |
| `test` | 测试与验收脚本 |
| `docs` | 文档 |
| `chore` | 配置、依赖、脚本 |

**规则**：一次提交只做一件事；提交信息第一行不超过 50 字；正文说清"问题—方案—影响"。
