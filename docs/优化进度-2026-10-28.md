## 一、今天完成的三件事

### ✅ S1｜SSE 流式输出 + 思考过程可视化（+2.0）

**改之前**：前端一次 `await fetch('/api/agent/chat')`，3.5–6 秒里页面上只有一行
"Agent 正在理解问题并调用工具计算…"，细则点名的"流式输出渲染、AI 思考状态可视化"拿不到分。

**改之后**：Agent 拆成**三阶段**（规划 → 执行工具 → 撰写回答），每一步都通过 SSE 推事件。

| 事件 | 触发时机 | 页面上看到什么 |
|---|---|---|
| `stage` | 进入阶段 | 顶部一行："理解问题 / 模型正在判断需要哪几步 / 基于工具结果撰写回答" |
| `plan` | 模型选出工具 | "本轮计划：查询维度与主题排行 → 查询情感统计" |
| `tool_start` | 即将执行 | 新插入一行步骤，徽章「运行中」（蓝点在呼吸） |
| `tool_done` | 执行完毕 | 变「完成 6ms」，补上结果摘要 |
| `token` | 模型每个文字分片 | 回答气泡逐字增长，带闪烁光标 |
| `answer_reset` | 数值校验不通过 | 回答被替换 + 黄色提示"已自动撤回" |
| `done` | 全流程结束 | 右侧渲染图表、证据、口径、局限 |

**实测（`ds_2023_all`，真实 DeepSeek）**

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 首屏有任何反馈 | 3.5–6.0s | **0.02s**（第一步事件） |
| 回答首字 | 等全部算完才出现 | 3.0–4.0s（工具跑完后开始逐字） |
| 可见的执行过程 | 无（只有一行等待文案） | 3 步工具，每步参数 + 真实耗时 |
| 回答文字分片 | 一次性 | 一轮 114–246 个分片 |

> 不吹"首字 <1s"：回答第一个字必须等工具跑完，仍是 3–4 秒。
> 真正的改进是**这 3–4 秒里用户看到的是真实进度**，而不是空转。

**降级保护**：流式通道不可用（代理缓冲/浏览器不支持）时，前端自动回退到原来的
`/api/agent/chat` 一次性接口，不会白屏。

### ✅ S4｜前端性能三项（+1.2）

| 问题 | 做法 | 实测 |
|---|---|---|
| 每页都拉 1001KB 的 `echarts.min.js` | 从 `base.html` 移到 `{% block vendor %}`，只在驾驶舱/工作台/洞察三页加载 | `/evidence`、`/data` 零请求 |

### ✅ 附带修掉 3 个会影响观感的问题

1. **多关键词检索恒为 0 条**
   Agent 传 `keywords="口味、难吃、物价、贵"` 时，被当成**一整串子串**去 LIKE，
   必然 0 条，模型于是老实回答"检索到 0 条"。改为按空格/逗号/顿号/竖线切词后 OR 匹配。
   影响：回答里不再出现"检索不到原文"这种自相矛盾的话。
2. **回答里混着 markdown `**` 和裸引用号**
   模型开始引用 `CMT-xxxx`，但渲染成纯文本（`**（CMT-91EA4D2CC0，小红书）`）。
   现在 `[CMT-xxxx]` 渲染成蓝色芯片，点开直接弹证据详情；`**`、`` ` `` 一律清掉。
   同时数值校验先剔除引用号再比对，避免十六进制串里的数字被误判成幻觉。
3. **"负面率 100%"这类伪发现**
   问题本身限定了 `sentiment=negative` 时，该范围内的负面率恒为 100%。
   已在写作提示词里明确："这是筛选造成的，不是发现，不要写成结论。"

# 第二天｜S2 RAG：混合检索 + 引用注入（+4.5）

**改之前**：Agent 只有 `search_comments`，本质是 `content LIKE '%关键词%'` 后按点赞排序。
问"宿舍最不满的是什么"，它只能找到字面含"宿舍"的评论，找不到"5 人间没有独立卫浴"这种
一个字都不重合的证据；回答因此只能复述统计数字，没有任何可点开的原文锚点。
评分表 RAG 6 分实际是空的。

**改之后**：新增 `campuspulse/rag.py`（约 480 行）+ 第 6 个工具 `retrieve_context`，
Agent 在撰写回答前**确定性**跑一次混合检索，把片段连同编号注入写作提示词，回答里
`[CMT-xxxxxxxx]` 可点开回跳原文。

## 一、检索链路（全部本地可复算，无外部向量服务）

| 环节 | 做法 | 说明 |
|---|---|---|
| 切块 | 一条评论 = 一个检索单元；>160 字按 160/30 重叠窗口切 | 平均 20 字，整条即语义完整，切碎反而丢上下文 |
| ① 稀疏 | jieba 分词 + BM25（k1=1.5, b=0.75） | 词面命中，可解释 |
| ② 扩展 | 领域同义词表 + 未登录词拆二元字组 | 宿舍↔寝室、食堂↔饭堂；"快递点"→"快递/递点" |
| ③ 稠密 | 字符 2/3-gram 哈希 1024 维 + TF-IDF + L2 归一 | 抗分词错误；>35% 文档出现的桶置零=向量侧停用词 |
| 融合 | 三路 min-max 归一后加权（0.60 / 0.30 / 0.10），RRF 为备选 | 权重来自标注集网格搜索，不是拍脑袋 |
| 重排 | 点赞热度、维度一致、字面命中，合计不超过 +12% | 只做微调，不许盖过相关性 |
| 注入 | 片段拼成【检索到的原文片段】进写作提示词 | 编号是唯一合法引用来源 |
| 校验 | `citation_check` 分 valid / invalid / unknown 三类核对 | 编造编号会被点名，不是悄悄放过 |

## 三、踩到并修掉的 4 个真问题

1. **RRF 把名次压平**：三路各取前 300 做 RRF 后，"宿舍"类问题的第 2 名是"建议什么专业呢"——
   向量榜里大量弱相关条目稀释了稀疏导出的强匹配。改归一化加权后该条掉出前 5。
2. **提问里的空壳词污染打分**：`什么 / 怎么样 / 学校 / 学生 / 能不能 / 有没有` 参与 BM25，
   一条只含"学生""什么"的短评论能靠长度归一化冲到前排。加查询侧停用词表后 P@5 从 0.667→0.817。
3. **未登录词必然 0 条**：jieba 把"快递点"当一个词，语料里写的是"快递站" → 检索返回一堆
   "在哪里写作业"。加"未登录 3 字以上词拆二元字组"后能召回"快递站"相关 5 条。
4. **统计口径与检索口径不一致**：统计限定了 `sentiment=negative + dimension=宿舍住宿`，
   检索却满库乱找，会出现"数字说宿舍负面最多、引用的是食堂好评"。现在检索复用工具已确定的筛选条件，
   命中不足 3 条时才放宽到全库并在页面标注。

# 第三天｜S5 商业与社会价值 + S8 MCP 解耦（+4.7）

## 一、S5：把"社会价值"从形容词变成数字

**改之前**：这块是空白，只有一句"面向学院评估"。评分表里 10% 的权重实际拿不到 4 分以上。

**改之后**：`docs/商业与社会价值.md`（约 300 行）+ `tools/value_metrics.py`（复算脚本）。

关键决定：**不写形容词，写可复算的数字**。文档里每句话都能用脚本跑出来，
答辩时被追问"这个数怎么来的"可以直接开终端。

### 1.1 找到了一个真实的拐点

2023 秋招季样本（2,567 条）按周切开，负面率是这样走的：

| 周次 | 负面率 | 当周最大负面维度 |
|---|---|---|
| W35（09-01~09-03） | 9.9% | 招生报考 (4) |
| W36（09-04~09-10） | 10.1% ← 基线 | 食堂餐饮 (9) |
| **W37（09-11~09-17）** | **25.9%（2.6 倍）** | **食堂餐饮 (48)** |
| W38–W39 | 20.1% / 25.9% | 食堂餐饮 |
| W40（10-02~10-08） | **48.6%** | 食堂餐饮 (32) |

由此得出"早发现"的量化口径：

- 周报在 **09-17** 就能看到跳变；月报要等 9 月结束、**10-01** 才出报 → **提前 14 天**；
- 月报还会**抹平拐点**：9 月整体 20.1%，看起来"还行"，但其中一周是 25.9%；
- 拐点之后累计 597 条负面，占该样本负面总量 747 条的 **79.9%**。

这里刻意没有写"提前 14 天就能避免多少损失"——**无法证明学校介入就一定压得住**。
能证明的只有"早 14 天看到，且不被月均值抹平"。这条边界在文档里明写了。

### 1.2 一个反直觉的发现

长期样本（1,803 条）的月份分布：

- 6–8 月占全年评论量的 **66.8%**（招生季，符合预期）；
- 但这三个月的负面率只有 **5.7%**，是全年最低；
- 9 月量只占 9.7%，负面率却是全年最高 **10.9%**。

也就是说 **量最大的时候风险最低，风险最高的时候量最小**。
只按"评论量"排序做监测，会刚好错过真正需要看的那批内容。

这个发现反过来验证了系统设计：驾驶舱和 Agent 一直是按"负面率 + 分母"排序，不是按热度排序。
之前这只是个实现选择，现在有了数据支撑。

### 1.3 商业部分：刻意跟"漂亮数字"反着来

同类材料常见的算法是把"普通高校 3,000 所 + 职业院校 1,500 所"相加得 4,500 所，
再乘 2 万得 9 亿 —— **这是重复计算**，高职专科本身就含在高等学校统计里。
本作品不做这种算法，改成分层：

| 层级 | 口径 | 数量 | 年单价 | 规模 |
|---|---|---|---|---|
| TAM | 全国高等学校 | 约 3,100 所 | 2.0 万 | 约 6,200 万/年 |
| SAM | 有独立宣传/学工部门与预算，40% 估 | 约 1,240 所 | 2.0 万 | 约 2,480 万/年 |
| SOM（3 年） | 广东约 160 所，渗透 10% | 约 16 所 | 2.0 万 | 约 32 万/年 |

并且明写了一句"**6,200 万不是高增长故事**"。这不是自黑——评委见过太多把 TAM 吹成十亿的材料，
主动承认市场小、但证明"需求稳定 + 预算真实存在 + 竞品不打这个价格带"，
比虚报数字更能说明想清楚了。

其余论断：
- **定价原则**：让学校用旧预算买新东西。现有舆情月报外包价 1–3 万/年，标准版定 2.0 万。
- **三档**：轻量 SaaS 1.2 万、标准 SaaS 2.0 万、私有化 8–15 万 + 15%/年运维。
  私有化是本项目天然优势（本地 SQLite + 单进程 Flask，本来就不连云），竞品要改架构。
- **竞品空档**四处：价格（5 万 → 1.2 万）、范围（全网 → 本校）、部署（SaaS → 可离线）、
  语义（品牌/竞品 → 招生季/宿舍/食堂）。
- **合规五条硬约束**落到代码：最小必要、展示层去标识化、数据不出校、不对个人评分排序、不判断事件真伪。

## 二、S8：MCP —— 把工具层从界面里解耦

**改之前**：6 个工具只有网页里的 Agent 在用。这类"工具调用"很难自证不是硬编码的 if-else，
评委也没法从界面看出工具层是独立的。

**改之后**：`tools/mcp_server.py` 把同一份 `TOOL_SPECS` 暴露成 MCP Server（stdio + JSON-RPC 2.0），
外加 `tools/mcp_client.py` 作为真实客户端做协议一致性自检。

### 2.1 没有引入 SDK

MCP 官方 Python SDK 会带进 pydantic 等一串传递依赖。本项目定位是"本地可离线运行"，
`requirements.txt` 至今只有 7 个依赖。所以**手写协议**：

| 方法 | 实现要点 |
|---|---|
| `initialize` | 版本协商（请求版本在支持列表内则回显，否则回落 `2024-11-05`）+ 下发 `instructions` 说明边界 |
| `notifications/*` | 严格按通知语义：无 `id` 就不回复 |
| `tools/list` | `TOOL_SPECS` 直接映射，字段只差 `parameters → inputSchema` |
| `tools/call` | 转发 `execute()`，校验/脱敏/口径全部继承 |
| `ping` / 未知方法 | 前者返回 `{}`，后者返回 `-32601` |

不装 SDK 的代价是"协议必须自己写对"，所以配了客户端来证明。

### 2.2 怎么证明它真的符合协议

`tools/mcp_client.py` 走的是**子进程 + 独立客户端**，不是 import 调函数——
它不认识 Flask、不认识 HTML、只认识 JSON-RPC。用 import 测出来的只是"函数能跑"。

```
一、握手        initialize 版本协商 · notifications 不回复
二、工具发现    tools/list 返回 6 个工具且 inputSchema 完整
三、工具执行    统计工具返回真实分母 1,803 · RAG 返回带 CMT 编号的片段
                非法枚举被拒 · limit=9999 收敛到 50 · 非整数明确报错 · 非白名单工具被拒
四、协议健壮性  未知方法返回 -32601 · ping 存活
五、优雅退出    stdin 关闭后退出码 0
→ 10/10 通过
```

答辩时的一句话：**同一套受控工具，网页里的 Agent 能调，Claude Desktop 也能调，
白名单、脱敏、分母披露全都自动继承——安全不是界面的属性，是工具层的属性。**

## 三、顺手修掉的一个真问题：Schema 声明了却不校验

写 MCP 客户端测试时发现：`search_comments` 传 `limit=9999`，返回成功。

追下去发现 `_validate_args()` **只做字段名白名单，不看 Schema 里的 `type / minimum / maximum`**。
`limit` 是被 `analytics.search_comments` 里的 `clamp` 兜住的，所以"看起来没事"。

对内部 Agent 这没问题（模型写 9999 不该让整轮失败）。但有两个隐患：

1. **对外部调用方是"声明了不兑现"**——`inputSchema` 里明明写了 `maximum: 50`，
   客户端据此做校验会以为 max 生效了；
2. `top_k="很多"` 这种会一路走到 `int()` 抛 `ValueError`，最后被兜底成一句"工具执行异常"，
   调用方根本不知道自己错在哪。

于是补上 `_as_int()` + `_INT_FIELDS`，并且**刻意区分四种情况**（这个区分本身是设计决策）：

| 情况 | 处理 | 理由 |
|---|---|---|
| 非法枚举（`platform="微博"`） | 拒绝 | 没有"最接近的合法值"，猜错比报错更糟 |
| 非整数（`top_k="很多"`、`limit=true`） | 拒绝并说明 | 沉默纠正会让调用方永远不知道接口用错了 |
| 超上限（`limit=9999`） | **收敛到 50**，不报错 | 模型手滑不该让整轮失败，但查询量绝不能真被放大 |
| 带单位（`limit="10条"`） | 解析为 10 | 模型的自然习惯，能安全解析就没必要退回重试 |

顺带发现技术说明 5.3 原来写"`limit=9999` 会被拒绝"，与实现不符，一并改正。
