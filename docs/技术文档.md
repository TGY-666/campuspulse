## 1. 项目概述

### 1.1 项目背景

高校的宣传、学工与后勤部门每天都在处理来自抖音、小红书的公开评论：食堂价格、宿舍条件、招生咨询、教学安排、实习就业、校园环境、交通出行、校园活动。真实工作流里，工作人员面对的往往不是“缺图表”，而是三个更具体的问题：

1. 这条负面信息**有多急**，值不值得今天处理？
2. 这件事**该找哪个部门**，责任人是谁？
3. 处理过程**有没有留痕**，事后能不能说清楚“凭什么这样判断”？

通用 BI 工具能回答“评论量是多少、负面占比多少”，但回答不了“归谁、多久之内、下一步做什么”。CampusPulse 在原有舆情分析系统之上，把统计结果继续推进到责任主体、响应时限与处置闭环。

### 1.2 项目定位

> 把公开平台评论，变成四件可以直接执行的事：**多急（风险指数）→ 归谁（归口部门）→ 多久之内（工作小时 SLA）→ 下一步做什么（建单/处理/复核/归档）**。

项目不是“再做一个大屏”，而是在真实采集数据与既有清洗口径之上，增加一层可解释、可追溯、可降级的 AI 能力：

- AI 只负责选择工具、组织语言，不负责计算数字；
- 所有数字来自后端统计接口，图表由后端确定性生成；
- 每条结论尽量落在“一个部门 + 一个时钟 + 一条证据”上；
- 模型不可用时，系统退回规则路由并如实标注，不伪装成 AI。

### 1.3 目标用户

| 用户 | 典型动作 | 系统提供的价值 |
|---|---|---|
| 校办值班负责人 | 每天看“今天哪些事该谁处理、多久之内” | 风险研判总览、归口建议、一键建单 |
| 归口部门处置员 | 只处理本部门相关事项 | 部门账号、工单处理、提交复核 |
| 分析员 / 只读角色 | 看总览、洞察与证据 | 数据集切换、筛选、报告、证据回跳 |
| 评审 / 第一次使用者 | 3–5 分钟看懂系统 | 六个一级入口、页面即阅读顺序、口径可展开 |

### 1.4 主要成果

| 成果 | 说明 |
|---|---|
| 12 个页面 | 6 个一级入口，覆盖总览、洞察、证据、数据、研判、Agent |
| 6 个受控工具 | 情感、主题、趋势、平台对比、评论检索、RAG 原文检索 |
| 4 个预设数据集 | 真实采集 + 按真实样本特征生成，首次启动自动入库 |
| 双工具通道 | 进程内直调 / MCP stdio，同一份工具规格与校验 |
| 多租户与工单 | 5 类角色、SQL 层租户隔离、工单状态机、工作小时 SLA |
| 可核验回答 | 数字白名单、引用编号校验、改写/剔除/标注 |
| 可部署 | Windows 一键脚本、WSGI、Docker、健康检查 |
| 验收体系 | 开发仓库 16 个验收脚本，覆盖端到端、协议、权限、安全、UI |

### 1.5 口径与术语

| 术语 | 定义 |
|---|---|
| 有效评论 | 通过清洗规则（去重、去空、去短评、去无关讨论）后进入统计的评论 |
| 原始评论 | 采集/导入得到的全部记录，包含重复、空内容、短评与无关讨论 |
| 主题 | 校园八类业务主题；一条评论可命中多个主题，因此主题计数是**多标签计数** |
| 情感 | 正面 / 中性 / 负面，由关键词规则标注，不是大模型判断 |
| 风险指数 | 0–100 的统计特征加权分，不是负面占比，也不代表对言论真实性的认定 |
| 工作小时 | 周一至周五 09:00–12:00、14:00–18:00，每天 7 个工作小时 |
| 引用编号 | `CMT-xxxxxxxx`，指向一条可回跳的脱敏评论证据 |
| 数据集版本 | `data_version` + 有效条数，用于判断缓存是否失效 |

## 2. 需求分析

### 2.1 业务场景

**场景一：值班负责人的早晨。** 打开系统先看总览：哪个主题风险最高、归口哪个部门、建议多久内响应。点进研判页能看到风险拆解（量级、负面率、增速、互动）和代表证据；确认后建单，工单进入“待确认 → 待分派 → 已分派”。整个过程不需要在群里问“这个归谁”。

**场景二：部门处置员处理工单。** 用部门账号登录，导航里只有“风险研判与处置中心 → 处置工单”。只看到归口本部门的工单；处理完提交复核，归档仍由管理员完成，避免“自己给自己结案”。

**场景三：分析员追问证据。** 在 Agent 页问“食堂最近负面多吗”，系统展示工具调用步骤、真实统计图、脱敏证据编号；点击编号回到证据页原文。回答中的数字都能在工具结果里找到。

**场景四：评审第一次打开。** 不需要培训：导航按“先看全局 → 再看细节 → 最后提问”排序；每个页面只回答一个问题；口径说明与空数据提示都在页面上。

### 2.2 功能需求

| 模块 | 核心功能 | 关键约束 |
|---|---|---|
| 舆情总览 | 数据集概况、情感结构、平台对比、风险提示、驾驶舱解读 | 数字带分母；AI 不改数字 |
| 数据洞察 | 主题热度、情感分析、时间趋势、词云、分布画像 | 主题为多标签计数；筛选可组合 |
| 热点与证据 | 评论检索、排序、详情、编号回跳 | 证据脱敏；不采集个人身份 |
| 数据与报告 | 文件导入、截图导入、实时采集、质量链路、AI 报告、Markdown 导出 | 导入先预览后入库；失败不留下空壳 |
| 风险研判 | 风险指数、等级、归口部门、建议、区间研判 | 风险可复算；只建议不自动建单 |
| 处置工单 | 建单、分派、处理、提交复核、归档、驳回、重开 | 状态机不许跳步；事件 append-only |
| AI 助手 | 自然语言提问、工具调用、图表、证据、引用核验 | 计算与生成解耦；统计、图表与证据由后端确定性产出 |
| 权限与多租户 | 登录、角色、部门账号、租户隔离 | 漏写 tenant_id 直接报错 |
| 采集与导入 | JSON 文件、截图 OCR、Playwright 实时采集 | 未就绪时通过状态提示与诊断码明确披露当前引擎 |
| 系统运维 | 健康检查、预热、日志、Docker 部署 | 单 worker + 多线程 |

### 2.3 非功能需求

| 维度 | 要求 | 实现 |
|---|---|---|
| 可解释性 | 每个数字能说清分母与来源 | `analytics.py` 统一口径；结果带 `meta` |
| 可控性 | 模型不能执行任意 SQL/命令 | 6 个白名单工具 + JSON Schema |
| 可追溯 | 回答引用可回跳；工单事件可审计 | `CMT-*` 锚点；`ticket_events` append-only |
| 安全性 | 密钥不入库；输入侧拦截注入/越权 | `.env` 排除；`guard.py` 四道闸 |
| 可用性 | 依赖可插拔、状态可观测、核心链路连续可用 | OCR/MCP/LLM 均有明确切换路径与诊断码 |
| 性能 | 首屏不转圈；重复提问不重复计费 | 预热、缓存、静态资源强缓存、gzip |
| 可部署 | Windows 本机 / Linux / Docker | `run.py` / `wsgi.py` / Dockerfile |
| 离线能力 | 核心功能不依赖外部服务 | 本地 ECharts、本地 RAG、SQLite |

### 2.4 关键设计约束

1. **计算与生成解耦。** 模型负责意图理解、工具规划与语言组织，统计、图表坐标、证据列表全部由后端确定性生成。
2. **校内数据边界优先。** 不加载外部 CDN；截图 OCR 优先本地推理，必要时通过受控接口接入外部模型。
3. **事实可追溯。** 结论只引用当前数据集与工具结果；空结果以结构化状态返回。
4. **能力状态透明。** OCR、Playwright、DeepSeek Key 缺失时通过诊断码、健康检查和界面提示披露当前引擎。
5. **结论落到责任主体与时限。** 风险研判输出证据、归口和 SLA，建单由业务责任人确认。
6. **议题级治理。** 工单聚焦公共议题与处置时限，采用脱敏证据，不对学生个体贴标签，不替代事实认定。

### 2.5 验收标准（摘要）

- 6 个一级入口在对应权限下均可访问，无死链；
- 数据集切换后，洞察页分母、有效率、图表同步变化；
- Agent 真实调用 6 个工具，返回 3 类图表与可回跳证据；
- 回答中的数字必须能在工具结果中找到；编造引用被标记/剔除；
- 非法参数、注入、越权取数被拦截，且不误杀正常问题；
- 工单状态机不允许跳步，事件不可修改；
- 多租户交叉访问 0 泄露；
- 未配置 Key / 未安装 OCR / 未安装 Playwright 时，页面如实提示；
- 深色模式对比度、移动端无横向溢出；
- 健康检查能区分当前引擎、工具通道、认证模式与采集状态。

## 3. 系统架构设计

### 3.1 总体架构

![CampusPulse 总体架构](architecture.png)

<p style="text-align:center;color:#64748b;font-size:9pt;margin-top:-1mm">图 3-1　CampusPulse 总体架构</p>

系统采用“浏览器 → Flask 应用层 → 三条业务主线”的分层结构。三条主线分别是 AI 编排、研判处置、数据统计；模型只通过 6 个白名单工具取值，本地通道与 MCP 通道共用同一份 `TOOL_SPECS` 和同一套参数校验、脱敏与口径披露。

### 3.2 分层职责

| 层 | 关键文件 | 职责 |
|---|---|---|
| 表现层 | `templates/*.html`、`static/cp/*.js`、`app.css` | 页面结构、交互、图表、主题、无障碍 |
| 应用层 | `web.py` | 路由、统一 JSON 信封、鉴权、安全头、静态资源 |
| AI 编排 | `agent.py` | 两阶段调用、工具选择、回答生成、降级 |
| 工具层 | `tools.py`、`toolbus.py`、`tools/mcp_server.py` | 白名单工具、Schema 校验、本地/MCP 通道 |
| 检索层 | `rag.py` | BM25、同义扩展、字符 n-gram 向量、RRF、引用锚点 |
| 可核验性 | `veracity.py`、`guard.py` | 引用/数字校验、输入侧注入与越权拦截 |
| 统计层 | `analytics.py` | 筛选、分母、比率、时间序列、分布、风险辅助 |
| 数据层 | `db.py`、`etl.py`、`taxonomy.py`、`legacy/data_processor.py` | SQLite、清洗、主题词典、情感规则、历史口径 |
| 研判处置 | `departments.py`、`tickets.py`、`monthly.py` | 风险指数、归口、区间研判、工单状态机 |
| 采集导入 | `crawl.py`、`intake.py`、`vision.py` | 实时采集、文件/截图导入会话、OCR |
| 报告图表 | `reports.py`、`charts.py` | AI 报告、规则版报告、确定性图表配置 |

### 3.3 数据流

```text
原始 JSON / 截图 / 实时采集
        │
        ▼
ETL 清洗（legacy/data_processor.py 规则 + etl.py）
  字段统一 → 去重 → 时间解析 → 无效评论判定
  → 主题匹配 → 情感标注 → 负面原因/正面卖点 → 脱敏
        │
        ▼
SQLite（datasets / comments / 质量报告 / 数据版本）
        │
        ├── analytics.py → 页面图表 / 报告 / 风险研判
        ├── rag.py       → Agent 检索证据
        └── departments.py / tickets.py / monthly.py → 归口与工单
```

### 3.4 数据库设计（核心表）

| 表 | 作用 | 关键字段 |
|---|---|---|
| `datasets` | 数据集元信息与质量报告 | `dataset_id, raw_count, valid_count, time_start, time_end, quality(JSON), data_version` |
| `comments` | 清洗后的评论（含被剔除记录） | `comment_ref, content_masked, comment_date, dimensions(JSON), sentiment, negative_reason, cleaning_status, filter_reason` |
| `reports` | AI/规则报告留痕 | `report_id, dataset_id, engine, content, created_at` |
| `agent_runs` | Agent 审计 | `run_id, dataset_id, question, engine, tool_steps, duration_ms` |
| `departments` | 归口部门与 SLA | `dept_id, name, dimensions(JSON), keywords(JSON), sla_hours` |
| `tickets` | 处置工单 | `ticket_id, status, priority, owner, due_at, rule_id, comment_ref` |
| `ticket_events` | 工单事件（append-only） | `ticket_id, action, from_status, to_status, actor, note, created_at` |
| `risk_runs` | 区间研判快照 | `run_id, dataset_id, date_from, date_to, topics(JSON)` |
| `users` | 账号与角色 | `user_id, username, password_hash, role, department_id, tenant_id` |
| `app_settings` | 租户级配置 | `tenant_id, key, value` |

> `comments` 保留被剔除记录（`cleaning_status ∈ {kept, too_short, empty, irrelevant}`），所以“这条为什么没算进来”可以逐条查，而不是黑箱。

### 3.5 接口设计

所有接口返回统一信封：

```json
{"ok": true, "data": {...}}
{"ok": false, "error": {"code": "bad_request", "message": "可读错误", "detail": "..."}}
```

- 列表接口统一返回 `items / total / page / page_size`；
- 统计接口统一返回 `meta`：`dataset_id / data_version / denominator / filters_text / time_span`；
- 错误码区分参数错误、权限错误、冲突、未找到、引擎不可用；
- 前端只处理一种结构，异常也能给出可读提示。

### 3.6 前端架构

- **Zero-Build 零构建链原生 ESM 模块化架构**：页面按路由拆分为 `dashboard.js`、`insights.js`、`evidence.js`、`data_collect.js`、`departments.js`、`tickets.js`、`agent.js` 等模块，配合共享运行时 `core.js` 消除打包冗余，实现 clone 即运行与静态资源强缓存。
- **统一运行时契约**：`core.js` 统一 REST 信封解包、`CPError` 异常体系、URL 状态双向同步与分享保持，并以 JSDoc 约束 Dataset / Filters / State / Error / ChartSpec 的跨页面流动。
- **按视口分级加载图表**：基于 `IntersectionObserver` 与自适应 `LAZY_MARGIN`，按容器状态机管理 `is-lazy-wait` / `is-stalled` / `is-failed`，在首屏性能、可感知进度与错误可恢复性之间取得平衡。
- **确定性可视化与导出链路**：`charts.py` 生成 categories/series，前端只负责渲染；`beforeprint` 自动执行 `flushAllCharts` 与 `renderPrintScope`，保证打印、截图和 PDF 导出前全量图表就绪。
- **可访问交互系统**：`NEG_DECAL` 以 45° 斜纹与语义色双编码负面段，模态框实现 Focus Trap，`WAI-ARIA Live Region` 实时播报加载、工具调用与错误状态，覆盖色觉差异与读屏场景。

### 3.7 部署架构

| 场景 | 入口 | 特点 |
|---|---|---|
| Windows 演示 | `start.bat` → `run.py` | 自动建 venv、装依赖、开登录与工单、自动开浏览器 |
| 本机调试 | `python run.py` | 端口顺延、预热、免登录 |
| Linux 生产 | `gunicorn wsgi:app` | 1 worker + 8 threads，`--timeout 120` |
| Windows 生产 | `waitress-serve wsgi:app` | 同上 |
| 容器 | Dockerfile / docker-compose | 全部功能镜像约 1.2GB（含 OCR / MCP / Chromium） |

**为什么必须 1 个 worker：**

1. SQLite 多进程写锁竞争会导致 ETL 偶发 `database is locked`；
2. MCP 子进程句柄是进程内单例，多 worker 会各起一份服务；
3. 检索索引与词频缓存按租户缓存在进程内存里，多进程会翻倍。

### 3.8 关键设计决策

| 决策 | 选择 | 工程收益 | 设计边界与适配策略 |
|---|---|---|---|
| 数据库 | SQLite（WAL） | 单文件、零运维、适配数千至数万条评论的校内私有化交付 | 生产部署采用单 worker + 多线程，确保写锁与缓存一致性 |
| 前端 | 原生 JS + JSDoc | Zero-Build 原生 ESM、启动快、跨页面契约集中于 `core.js` | 以共享运行时与约定式组件复用控制前端复杂度 |
| Agent | 两阶段 Function Calling | 固定预算、可观测、可审计，适配校内确定性验证 | 将开放式推理收敛为受控工具工作流，保留按需接入模型的扩展位 |
| RAG | 本地三路召回 | 离线、可复算、零 GPU 与外部向量服务依赖 | 以领域同义词、字符 n-gram 与 `EMBEDDING_HOOK` 形成渐进式扩展路径 |
| 情感/主题 | 高确定性领域词典规则 | 秒级全量批处理、标签可解释、与统计口径天然一致 | 与大模型上下文推理协同覆盖复杂长尾表达 |
| 工单 | 状态机 + append-only | 可审计、防跳步、人工在环确认责任边界 | 状态迁移集中配置，便于按学校治理流程演进 |
| 降级 | 规则路由 / 本地直调 | 无外部服务时仍保持统计、图表与证据链连续可用 | 健康检查披露当前引擎，按需切换 DeepSeek、MCP、OCR 与采集能力 |

## 4. AI 技术方案

### 4.1 选型理由

#### 4.1.1 大模型：DeepSeek Chat

| 维度 | 考虑 | 结论 |
|---|---|---|
| 中文能力 | 校园评论、报告写作以中文为主 | 中文表达稳定 |
| Function Calling | 需要模型选择工具、填 JSON 参数 | 原生支持 OpenAI 风格工具调用 |
| 成本 | 演示与答辩需要反复提问 | 价格低，适合高频演示 |
| 兼容性 | 需要可替换、可降级 | OpenAI 兼容接口，可切网关 |
| 可控性 | 不能把数字交给模型 | 只让模型选工具与写文字 |

**模型与事实库解耦。** 模型通过受控工具读取实时统计与检索结果，回答中的数字、证据与图表均由后端事实集合约束。

#### 4.1.2 Agent 形态：受控分阶段 Function Calling 流水线

- **规划阶段**：模型负责识别意图、选择工具并填充 JSON 参数；
- **执行阶段**：后端依据 Schema 校验参数，调用真实统计、检索与图表构建逻辑；
- **生成阶段**：模型只基于工具结果组织 2–5 句可核验回答，引用与数字随后进入双核验；
- **工程价值**：将计算、生成、审计与降级解耦，形成可追溯的确定性流水线；阶段预算、调用次数和错误边界均可观测，适配高校私有化交付的稳定性要求。

#### 4.1.3 RAG：面向零 GPU 算力门槛的本地三路混合检索架构

| 方案 | 工程收益 | 适配策略 | 是否采用 |
|---|---|---|---|
| 纯关键词 LIKE | 实现成本低 | 作为精确过滤的基础能力 | 否 |
| 外部向量数据库 | 语义服务能力强 | 增加网络与运维依赖 | 否 |
| 本地 BM25 + 同义扩展 + 字符 n-gram | 离线、可复算、毫秒级确定性召回 | 领域词典与哈希向量协同 | 是 |
| 稠密向量扩展 | 提升长尾语义覆盖 | 通过 `EMBEDDING_HOOK` 保留替换点 | 预留 |

当前实现以 1024 维 CRC32 字符 2/3-gram TF-IDF 为第三路召回，配合同义词扩展与 BM25，兼顾校内私有化低成本部署、确定性延迟和可演进接口。该设计把向量模型依赖隔离在可插拔钩子之后，后续接入本地句向量时无需改动上层 RRF、引用与审计链路。

#### 4.1.4 OCR：RapidOCR ONNX

- 选择 `rapidocr_onnxruntime` 而不是 PaddleOCR：纯 ONNX 推理，不需要 Paddle 全套框架，Windows/Linux 都能直接 pip 安装；
- 首次运行自动下载约 15MB 检测/识别模型，之后完全离线；
- 识别结果先进“待复核”草稿，人工确认后才入库，并保留 `ocr_confidence` 与 `ocr_engine`；
- 未安装时明确提示“未检测到 OCR 引擎”，而不是返回“导入成功 0 条”。

#### 4.1.5 MCP：手写 JSON-RPC，而不是引入 SDK

- MCP 核心是 JSON-RPC 2.0 over stdio，本项目只需要 `initialize / tools/list / tools/call` 三个方法；
- 手写约 200 行标准库实现，透明、可读、无传递依赖；
- 同一份 `TOOL_SPECS` 与 `tools.execute()` 同时服务网页 Agent 与外部 MCP 客户端，避免“两套实现”。

### 4.2 集成方式

#### 4.2.1 Agent 调用链

```text
用户问题
  │
  ├─ ( 输入侧四道闸
  │     长度 ≤ 200 字
  │     同一来源每分钟 ≤ 20 次
  │     注入 / 套提示词 / 越权取数 → 拒绝（只给类别，不给规则 id）
  │     归一化：NFKC + 去零宽 + 紧凑串
  │
  ├─ 1 第一阶段：DeepSeek Function Calling
  │     系统提示词注入：数据集、主题清单、术语、硬性规则
  │     模型只输出工具名与参数，不写回答
  │
  ├─ ) 后端执行工具
  │     tools.execute(name, args, ctx)
  │     JSON Schema 校验 → 统计/检索 → 结构化结果
  │     返回：summary / metrics / evidence / data / data_version
  │
  ├─ ( 第二阶段：模型基于工具结果写回答
  │     只能使用结果中出现过的数字
  │     2–5 句，先结论后依据
  │
  ├─ 2 引用与数字核验
  │     CMT-* 分类：valid / invalid / unknown
  │     数字白名单：回答中的数字必须能在结果中找到
  │     pass / revised / stripped / flagged / unverified
  │
  └─ ) 图表与证据
         charts.py 根据工具 data 生成 3 类图表
         evidence 带 comment_ref，可回跳证据页
```

#### 4.2.2 工具规格与校验

每个工具都有显式 JSON Schema：

```json
{
  "name": "get_topic_stats",
  "description": "统计 8 类校园主题的评论量排行，以及负面原因和正面卖点排行",
  "parameters": {
    "type": "object",
    "properties": {
      "dataset_id": {"type": "string"},
      "platform": {"type": "array", "items": {"type": "string", "enum": ["抖音", "小红书"]}},
      "dimension": {"type": "array", "items": {"type": "string", "enum": ["宿舍住宿", "..."]}},
      "top_n": {"type": "integer", "minimum": 1, "maximum": 20}
    }
  }
}
```

- 参数先校验再执行，绝不把模型给的字符串拼进 SQL；
- 只允许调用 6 个白名单函数，不能执行任意 SQL/Python/系统命令；
- 每次调用返回“参数回显 + 分母 + 数据版本”，让回答可复核；
- 失败返回结构化错误（`ok=false + reason`），由 Agent 转成用户能读懂的提示。

#### 4.2.3 确定性图表

`charts.py` 只做一件事：把工具返回的 `data` 转成 ECharts 配置。模型不生成 categories/series，因此即使模型输出跑偏，图也不会画错。每张图带 `caption`，写明分母与统计口径。

#### 4.2.4 报告生成

- 报告中的数字来自 `analytics.py` 的真实聚合；
- 模型只负责把数字写成可读分析与建议；
- 模型不可用时，用同一批统计生成规则版报告，并明确标注“统计规则生成，非 AI 分析”；
- 报告可按 Markdown 导出，带数据版本与筛选条件。

### 4.3 RAG 三路混合检索

#### 4.3.1 查询净化、三路召回与融合

检索入口先通过 `_QUERY_STOP` 剥离“请问、帮我分析、最近怎么样”等提问空壳词，再对未登录三字以上专有名词执行 `_oov_split`，切分为字符二元组，增强“快递点/快递站”等校园口语词的召回稳定性。随后并行执行：

1. **BM25 词项召回**：jieba 分词，`k1=1.5`、`b=0.75`；
2. **领域同义词扩展**：按校园词典扩展查询后重新计算 BM25；
3. **字符哈希向量召回**：1024 维 CRC32 2/3-gram TF-IDF，L2 归一化余弦相似度。

向量矩阵构建时统计每个哈希桶的文档频率，将超过 35% 文档出现的高频泛化桶置零，形成向量侧停用词机制，降低“学校、学生”等泛化片段对排序的干扰。

#### 4.3.2 网格搜索融合与受限重排

系统支持 RRF 与 Min-Max 归一化加权融合双算子切换。RRF 使用 `k=60`，每路保留前 300 名；加权融合的参数由 `tests/rag_eval.py` 在校园标注集上网格搜索得到：

`BM25 (0.60) + 同义词扩展 (0.30) + 字符向量 (0.10)`

在标注集上达到 `P@5 = 0.817`、`MRR = 0.958`。最终采用受限元数据重排：

`0.88 × 相关性 + 0.12 × 元数据加成上限`

其中元数据加成上限由点赞代表性 `0.06`、主题命中 `0.04`、字面命中 `0.02` 构成，兼顾高赞样本代表性与语义严谨性，避免元数据权重反客为主。

#### 4.3.3 引用锚点

每个片段都带 `comment_ref`。回答里写 `[CMT-xxxxxxxx]` 就能一键回跳证据详情。`veracity.classify()` 会把引用分成：

- `valid`：在本次检索结果里，可回跳；
- `invalid`：库里存在，但本次未检索到；
- `unknown`：库里不存在。

处理策略是一次受控重写；仍不成立时由 `strip_refs` 无损剥离编号并保留句子，同时在核验结果中记录处理状态。

### 4.4 AI 安全与可控性：输入护栏 + 输出双核验

#### 4.4.1 输入侧组合规则护栏

`guard.py` 对输入执行 NFKC 归一化、零宽字符剥离与紧凑串构造，再以“动作词 + 对象词”共现组合规则识别注入、套提示词和越权取数意图。单词在正常业务语境中可自由出现，组合命中才进入拦截流程；拦截事件写入 `guard_events` 审计表，客户端只收到类别化原因，不泄露规则 ID。

| 闸 | 规则 | 目的 |
|---|---|---|
| 长度 | 单条提问 ≤ 200 字 | 控制上下文与推理成本 |
| 频次 | 同一来源每分钟 ≤ 20 次 | 保护服务稳定性 |
| 意图 | 动作词与对象词组合命中 | 拦截注入、越权与数据外带 |
| 展示 | 输出前再次脱敏 | 保护评论与账号边界 |

#### 4.4.2 输出侧双核验

`veracity.py` 先执行引用锚点 `valid / invalid / unknown` 三态分类，再按 `REVISE_SYSTEM_PROMPT` 进行单次受控重写；仍有问题时使用 `strip_refs` 无损清理标点与引用编号。数字通过 `number_check` 白名单校验，支持四舍五入 ±1% 容差与受控合法差值派生，确保自然语言表达与后端事实集合一致。核验状态以 `pass / revised / stripped / no_anchor / flagged / unverified` 对外呈现，整个链路具备可审计的失败边界。

#### 4.4.3 多租户隔离

- 5 类角色、权限点集中在一个字典；
- `db.get_conn()` 返回 `TenantConn` 包装器，检查受保护表 SQL 是否漏掉 `tenant_id`；
- 开发模式下漏写直接抛 `TenantLeakError`，生产模式记录并由健康检查暴露计数；
- 越权矩阵测试覆盖 32 次交叉访问，期望拦截 32 / 泄露 0。

### 4.5 优化策略

1. **两阶段提示词分工。** 第一阶段只选工具，第二阶段只写回答，避免模型在同一轮里边算边编。
2. **工具描述即目录。** 主题清单从 `config.DIMENSIONS` 动态拼接，新增主题时模型能立即发现。
3. **工具调用预算。** 单轮最多 6 次工具调用；同一工具同参数只调用一次；`search_comments` 与 `retrieve_context` 每轮最多各 1 次，防止“多找几条”式重复检索。
4. **缓存按数据版本。** 报告缓存键包含 `data_version + 有效条数 + 筛选条件`，数据不变就不重复问模型；数据一变自动失效。
5. **启动预热。** 词典、检索索引、首次统计查询提前跑完，避免第一次点开转圈。
6. **静态资源强缓存。** URL 带文件 mtime，命中一年强缓存；gzip 压缩；ECharts 懒初始化。
7. **RAG 参数可复算。** BM25 参数、RRF k、召回深度、重排权重都写在模块顶部，验收脚本可对比调整前后效果。
8. **报告事实约束。** 报告生成前先构造 facts 白名单，模型输出后校验数字；未通过的数字会被标记或删除。
9. **规则优先、模型补充。** 归口判断先规则命中，模型只在候选部门之间选择，且 dept_id 必须存在于候选集合，否则回退规则。

### 4.6 多模态：截图评论导入

```text
PNG/JPG
  → 本地 OCR（RapidOCR）
  → 文本行 + 逐行置信度
  → 行分类：正文 / 时间地区 / 界面噪声
  → 正文成组（折行合并）+ 就近取发布时间
  → 草稿 {content, create_time, platform, confidence}
  → 人工复核
  → ETL 清洗
  → 数据集
```

三个约束：

1. **本地优先与可插拔推理**：首选本地 OCR；需要外部视觉模型时通过受控接口切换并披露引擎状态；
2. **人机协同复核**：识别结果进入待复核草稿，人工确认后才入库；
3. **状态透明**：没有 OCR 引擎时返回明确错误与安装指引。

### 4.7 MCP 工具通道

- `CP_TOOL_CHANNEL=local`：进程内直调，零开销；
- `CP_TOOL_CHANNEL=mcp`：JSON-RPC over stdio → 常驻子进程 → `tools.execute()`；
- 两条通道最后落到同一个 `tools.execute()`，参数白名单、Schema 校验、脱敏、口径披露完全一致；
- 子进程懒启动、加锁串行、失败自动重启一次，仍失败则降级本地直调并明确告知调用方；
- 开发仓库的 `tests/test_mcp_channel.py` 对同一批问题逐字段比对本地与 MCP 返回结果，避免“支持 MCP”变成一句空话。

### 4.8 AI 能力边界与演进接口

- 情感与主题由高确定性校园词典规则完成，模型聚焦复杂长尾问答、归口解释与自然语言组织；
- 风险指数是统计特征加权，输出量级、负面率、增速、互动及置信度分解，便于人工复核；
- RAG 以本地字符 n-gram 混合检索为默认实现，并通过 `EMBEDDING_HOOK` 预留稠密向量接入点；
- 结论严格绑定当前数据集、时间窗口、筛选条件与数据版本，不跨范围外推；
- 空结果、引擎状态与引用核验状态均通过结构化字段和界面提示呈现。

## 5. 核心功能实现

### 5.1 数据采集与导入

**文件导入**：上传 JSON → 落进 `data/uploads/_pending/<sid>/` → 清洗但**不写库** → 逐条核对通过/剔除及原因 → `commit` 才建数据集，`discard` 删除暂存目录。预览期不建 `ds_*` 目录、不写 `datasets` 行，形成可回滚的导入事务边界。

**截图导入**：本地 OCR → 草稿 → 人工复核 → ETL → 数据集；每条记录带 `ocr_confidence` 与 `ocr_engine`，支撑多模态数据接入与证据追溯。

**实时采集**：Playwright 真浏览器 → 搜索页 → 详情页 → 拦平台评论接口 → 原始记录 → 与文件导入共用清洗链路 → 人工确认 → 入库。未配置登录态时直接报 `need_login`，状态机将采集能力与数据质量边界清晰呈现。

### 5.2 清洗与统计

清洗链路复用原系统 `legacy/data_processor.py` 的规则：

1. 字段统一（平台、正文、时间、点赞、来源）；
2. 去重；
3. 时间解析与窗口过滤；
4. 无效评论判定（空内容、短评、无关讨论）；
5. 主题匹配（8 类，多标签）；
6. 情感标注（正/中/负）；
7. 负面原因 / 正面卖点；
8. 脱敏与引用编号生成。

统计层 `analytics.py` 是唯一口径来源：

- 所有筛选条件先校验再拼 SQL；
- 每个统计结果带 `denominator`、`filters_text`、`data_version`；
- 主题计数是多标签计数，占比分母是有效评论数；
- 时间序列按跨度自动选择日/周/月粒度；
- 平台对比在样本量差距大时提示可比性有限。

### 5.3 可视化与交互体验

- 后端生成图表配置，前端渲染；支持饼图、柱状图、折线图、横向排行与词云；
- `core.js` 以 `IntersectionObserver` + `LAZY_MARGIN` 执行视口分级懒加载，并以 `is-lazy-wait` / `is-stalled` / `is-failed` 细化容器状态；
- `beforeprint` 自动调用 `flushAllCharts` 与 `renderPrintScope`，打印、截图和导出前完成全量渲染；
- `NEG_DECAL` 以 45° 斜纹叠加红色语义色，建立红绿色觉差异下仍可辨识的双编码；
- 模态框提供完整 Focus Trap，`WAI-ARIA Live Region` 播报加载、错误和 AI 工具步骤；移动端断点与空数据状态均有明确反馈。

### 5.4 风险研判

风险指数由四项可复算的量加权：

| 分项 | 权重 | 满分参考 | 说明 |
|---|---|---|---|
| 量级 | 35% | 负面 60 条 | 负面评论数量 |
| 负面率 | 30% | 35% | 该主题负面占比 |
| 增速 | 15% | 近 30 天 / 前 30 天 = 2.0 | 与紧邻等长区间对比 |
| 互动 | 20% | 负面平均赞 200 | 传播潜力 |

计算：

```text
raw = 0.35 * 量级 + 0.30 * 负面率 + 0.15 * 增速 + 0.20 * 互动
score = 100 * raw * (0.55 + 0.45 * 置信度)
```

置信度由该主题样本量决定（30 条视作满分）。风险等级：

| 分数 | 等级 | 建议优先级 |
|---|---|---|
| ≥ 70 | 高 | P1；若 ≥ 85 且负面 ≥ 60，则 P0 |
| 50–69 | 中高 | P2 |
| 30–49 | 中 | P3 |
| < 30 | 低 | P3 |

归口判断先规则、后模型：部门表配置 `dimensions`（主责主题）与 `keywords`（同主题多部门细分）；规则命中直接出结果；模型只在两三个候选部门之间选择，且 `dept_id` 必须存在于候选集合，否则回退规则。

**只建议，不建单。** 风险研判产出建议与证据，工单由人在页面上点击生成。

### 5.5 处置工单

状态机：

| 动作 | 起始状态 | 目标状态 | 允许角色 | 额外要求 |
|---|---|---|---|---|
| 确认有效 | draft | triaged | analyst / admin | — |
| 驳回 | draft / triaged | rejected | analyst / admin | 备注 |
| 分派 | triaged | assigned | admin | 负责人 |
| 开始处理 | assigned | processing | handler / dept / admin | — |
| 退回重分 | assigned | triaged | admin | 备注 |
| 提交复核 | processing | pending_review | handler / dept / admin | 处理记录 ≥ 10 字 |
| 复核通过 | pending_review | closed | admin | 备注 |
| 复核不通过 | pending_review | reopened | admin | 备注 |
| 重新打开 | closed | reopened | admin | 7 天内 |
| 重新处理 | reopened | processing | handler / dept / admin | — |

**工作小时 SLA：** 只累计周一至周五 09:00–12:00、14:00–18:00，每天 7 个工作小时。P0 首次响应 1 小时、归档 4 小时；P1 首次响应 4 小时、归档 1 个工作日；P2/P3 依次放宽。节假日默认空，不猜测。

**审计：** `ticket_events` 在数据库层挂触发器，UPDATE/DELETE 一律被 SQLite 拒绝；每次状态变更都留一条事件，时间线可查。

### 5.6 区间研判

- 窗口是一段明确的起止日期，不是滚动 30 天；
- 增速项对比紧邻的等长区间；恰好整月时按上一个自然月比；
- 结论落库到 `risk_runs`，`topics` 存整份 JSON 快照，评论重新导入也不会失效；
- 定时任务每月初跑“上个月”，手动研判可选任意区间；
- 研判只产出结论，开单由人点；快照里记录“这段区间哪些主题已经有单了”，避免重复建单。

### 5.7 AI 舆情助手与交互模式创新

Agent 页面采用 SSE 实时流式输出：首字延迟（TTFT）在运行面板中回显，工具调用步骤、状态与耗时逐项点亮，回答、图表、证据和引用核验结果按事件流渐进呈现。后端的 `_ai_error_notice` 将网络、模型与工具异常转换为可读诊断码，前端通过错误边界优雅降级到规则路由或一次性分析。

**对话即筛选（Conversational Filter Carry-over / 生成式 UI 跨视图联动）**是本项目的交互创新。Agent 通过 `_pick_richest_meta` 从多步工具结果中选择最具体的筛选上下文，再由 `_carry_to_views` 将主题、情感、平台、时间窗口编码为带状态参数的跳转链接。用户可从自然语言问答直接进入全局驾驶舱或洞察中心继续深钻，筛选条件在 URL 中双向同步并可分享。

页面同时展示工具参数、结果摘要、证据 `comment_ref`、引用核验角标与语音转写状态，形成流式输出、AI 思考状态可视化和错误边界处理优雅的完整 AI 交互体验。

在 DeepSeek 未配置或暂时不可用时，规则路由仍会把本轮 RAG 命中的前 3 个真实 `CMT-*` 编号补入正文，并经过同一套 `veracity` 核验；因此离线演示依然保留“统计结论—原文证据—引用状态”的可见闭环。

### 7.2 工程架构权衡与设计边界（Architectural Trade-offs）

1. **高确定性领域词典规则 + 大模型按需深度推理**：情感与主题先由八大校园主题词典和高确定性规则完成秒级全量批处理，模型聚焦复杂长尾问答、归口解释与自然语言组织，在零 GPU 私有化场景下兼顾吞吐、可解释性与语义深度。
2. **轻量化字符 n-gram 混合检索 + `EMBEDDING_HOOK` 扩展接口**：BM25、同义扩展和 1024 维字符向量提供可复算的本地召回；向量来源通过钩子隔离，接入校内稠密模型时保留现有融合、引用与审计协议。
3. **受控分阶段 Function Calling 流水线**：以固定阶段预算替代自由循环多 Agent，保证每次工具调用均可观测、可回放、可审计，适合竞赛评审与校内生产环境的确定性验证。
4. **人工在环（Human-in-the-Loop）的工单决策确认**：系统提供风险证据、责任部门、SLA 和建议动作，建单、分派、复核和归档由具备权限的责任人确认，将公共议题治理的判断权保留在业务主体手中。
5. **单文件 SQLite + 单 worker 多线程**：以低运维成本换取部署一致性，配合 WAL、租户 SQL 守卫和 append-only 事件表，满足万级评论与多角色演示的稳定交付。

### 7.3 展望

- **语义检索升级**：接入本地句向量模型或学校私有向量库，保留现有 RRF 与引用逻辑；
- **模型评测体系**：建立问题集与人工评分，持续对比不同模型、提示词与检索参数；
- **更多平台与模态**：在合规前提下扩展平台，增加视频/语音转写；
- **校内系统集成**：与 OA、工单、统一身份认证对接，形成真正的处置闭环；
- **私有化部署**：支持校内离线模型与国产化环境；
- **数据治理**：增加数据血缘、字段级审计与更细粒度的租户策略。

## 8. 创新点说明

### 8.1 技术创新点

1. **计算与生成解耦的受控 Agent**：模型完成意图理解、工具规划与语言组织，统计、图表、证据由后端确定性生成；对应 AI 技术深度中的大模型集成质量与 Agent/工作流设计。
2. **本地三路混合 RAG**：查询净化、未登录词二元切分、BM25、同义扩展、1024 维字符向量、RRF/加权双算子与受限重排形成闭环；校园标注集达到 `P@5=0.817`、`MRR=0.958`。
3. **引用与数字双核验**：`valid / invalid / unknown` 引用分类、一次受控重写、`strip_refs` 无损剥离与 ±1% 数值白名单，建立可审计的 AI 安全与可控性边界。
4. **MCP 标准协议双通道**：网页 Agent 与外部 MCP 客户端复用同一份 `TOOL_SPECS` 与 `tools.execute()`，实现工具集成一致性。
5. **多模态证据接入**：截图 OCR、草稿复核、ETL 与引用锚点串成可追溯链路，覆盖文件、截图和实时采集三类入口。
6. **生成式 UI 跨视图联动**：`_pick_richest_meta` + `_carry_to_views` 将对话上下文转为状态 URL，形成“对话即筛选”的交互模式创新。

### 8.2 应用创新点

1. **从洞察到协同治理**：系统把评论聚合推进到责任部门、响应时限、证据回跳和工单状态机。
2. **可复算风险指数**：量级 35% + 负面率 30% + 增速 15% + 互动 20%，分子分母与数据版本随结果返回。
3. **部门专席的最小权限闭环**：部门账号仅处理归口范围内议题，复核归档由管理员完成。
4. **区间研判快照 + 人工在环**：窗口、结论、已有工单和处理动作均可回放，业务责任人保留最终决策权。
5. **可部署与可持续交付**：Zero-Build 前端、单文件 SQLite、Docker/WSGI/Windows 一键启动，降低高校私有化交付门槛。
